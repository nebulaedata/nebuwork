# Workflow 样式与运行场景交付（2026-10-16）

## 使用方式

NebuWork 的独立 Workflow 配置页和专家 SOP 中的真实 Workflow 使用相同的四项概览：执行流程、运行场景、输入参数、产物文件。概览读取当前账号的真实流程和产物；标准化流程保留既有业务描述。

页面字体、颜色、边框和控件继承系统样式。产物卡显示数量及最近三项，完整列表同时展示任务产物与工作流共享文件，包含文件名、大小、步骤、执行次数、时间和有效状态；预览、下载仍经过 Java 的账号校验。

点击“运行场景”可新增、复制、删除和排序场景，编辑名称、用途、完整 JSON 以及逐项参数说明。第一项是默认场景。点击“应用到流程草稿”后，再使用页面顶部始终可见的“保存流程”；未保存的流程或源码不能运行。保存冲突保留草稿及原版本，不自动覆盖。

运行时默认填好首个场景的 JSON。可选择其他场景，按说明修改，再直接运行；当前弹窗会分别保留每个场景的输入草稿，“恢复预设”只重置当前场景。修改不会自动写回保存的配置。JSON 语法错误显示位置并阻止提交。

3.5 独立界面提供同样的配置与输入体验，保留“仅创建”和“创建并运行”。创建及启动各自使用稳定命令标识；遇到响应丢失，用原输入重试会复用原请求。NebuWork 保留已有 Java 持久化创建并启动行为。

## 数据协议

在现有 `workflow.json` 定义中增加可选 `input_presets`，无需新表或迁移：

```json
{
  "input_presets": [
    {
      "id": "text_processing",
      "name": "文本处理",
      "description": "处理指定文本",
      "input": { "text": "示例内容", "options": { "enabled": false } },
      "fields": {
        "/text": "需要处理的文本",
        "/options": "处理选项",
        "/options/enabled": "是否启用附加处理"
      }
    }
  ]
}
```

上例仅解释协议，不写入任何业务工作流。每项包含 `id/name/description/input/fields`；ID 唯一且稳定，遵循现有标识规则。`input` 支持对象、数组和标量；`null` 仍按现有引擎规则转换为空对象。

`fields` 使用 JSON Pointer：`/sources/0` 表示数组第一项；字段名中的 `~` 写为 `~0`，`/` 写为 `~1`，空路径表示整个输入。校验器拒绝重复 ID、错误结构、无效或不存在的字段路径和非有限数字。未填写的说明在界面中明确显示，不自动猜测。编辑 JSON 移除字段后，应用时清理对应的过期说明。

预设随定义校验、保存、复制、历史恢复和任务定义快照保留。缺失属性与空数组均表示没有预设，历史流程不自动补齐。

Java 继续透传完整 `definition` 和 `expected_revision`，运行仍提交 `{ "input": 用户最终输入 }`；不传入整个预设对象。账号隔离、POST 网关路径、下载鉴权和任务幂等机制沿用既有接口。

3.5 构建助手及 MCP 指南已要求：生成或修改业务代码时，根据实际输入契约保存场景、完整输入和中文说明，校验后再交付。未知业务值明确标为待配置，不编造场景，不固定套用“初始化／增量更新”；仅构建请求不会触发执行。

## 更新顺序

1. 先更新 3.5 服务，使其支持并保留 `input_presets`，同步更新其独立前端。
2. 再更新 NebuWork 前端。Java 业务接口不需要变更；新增集成回归用例验证其透传与账号隔离。
3. 不需要数据库迁移，不批量修改已有业务流程文件，不创建示例任务或执行采集。用户明确要求补齐某条流程时，读取其实际代码，通过带版本校验的定义接口单独保存。

两端的 `inputPresets.ts`、`InputPresetControls.tsx`、`inputPresets.css` 保持相同实现。后续调整协议或交互时需同步更新两个仓库。组件与工具文件使用不同主文件名，避免 Windows 上省略扩展名的导入优先匹配到同名 `.ts` 文件。
